## Context

`loadPlugin` (`runtime/plugin.go:165-192`) runs `Init`, then `applyVocabulary(env)` over the registration view, then diffs a before/after snapshot. `applyVocabulary`:

1. builds `goFuncs` from every `LocalNames()` entry (unsized map);
2. on an empty base, deletes every GoFunc not in the vocabulary;
3. `Set`s every vocabulary entry, whichever plugin is loading;
4. under Lisp-2, walks `LocalNames()` again and `SetFunc`s every GoFunc whose function cell is absent or equal (equal cells are rewritten, each costing a journal record and a cell version bump).

The lazy path applies (3) and the allowlist per registered value and binds function cells at materialization.

## Decisions

### One decision function in core

A core function takes the dialect and one registered `(name, value, canonical)` and returns the bindings to make: zero or more value-cell names (the registered name unless the allowlist drops it, plus every vocabulary alias whose canonical name matches), whether each is canonical, and whether to mirror each into the function cell. Runtime eager and lazy paths only execute that plan. Adapters are dialect-owned bindings ensured per operation only when absent, never rewritten (binding them at `New` would charge every default CL engine's meter outside any eval and make them survive `UnloadPlugin`).

### Scope to the operation

The eager pass runs over the value-cell names this operation wrote through its registration view, read from the journal via `(*core.Registration).Names()`; the name-only `loadPlugin` snapshot cannot see names `Init` overwrote. A vocabulary alias is (re)bound only when its canonical name is in that set. Only names this operation wrote are processed; for each, the function cell is written unless it holds a live value not `Equals` to the new one (the defun-revert guard). `GoFunc.Equals` compares names only, so equal cells are still rewritten to pick up a new `Fn`.

### Renamed names a plugin also registers

When a vocabulary renames a visible name to a canonical one (`count` -> `first`) and a plugin registers the visible name itself, the current behavior is kept on both paths: the plugin's own binding stays unless the operation also registers the canonical name, in which case the rename alias wins. The result is independent of registration order. The eager pass runs in two phases, own bindings first and aliases second; an alias write replaces a cell this operation itself wrote without consulting the defun-revert guard, which applies only to cells the operation did not write. The lazy path gives an alias entry precedence over an own entry under the same name.

### Host bindings

The allowlist filters plugin registrations as they happen. Nothing deletes existing root bindings afterwards, so `Bind` values survive any later plugin operation. This matches ADR 0005: the allowlist restricts what plugins expose to rule code; the host is trusted.

## Risks

- A host that relied on the allowlist deleting its own earlier `Bind` values: none known; the behavior was order-dependent.
- The core decision function becomes public surface for core-only embedders; keep it minimal (one function, one small result type).
