## Context

Both probes ran against the current tree from a scratch module with a `replace` directive: the singleton mutation reproduced with an unchanged fingerprint, and the two vocabularies hashed equal.

## Decisions

- **Copy on read** for `Vocab()`: callers are construction-time (`applyVocabulary` once per plugin load; the lazy `RegisterValue` once per registered builtin inside a template build that is single-flighted once per process per dialect fingerprint and plugin), so the copies are bounded and off the eval path. `maps.Clone` preserves nil versus empty, which both runtime paths depend on (nil = identity, empty non-nil = strip everything on an empty base). `VocabEntry(name)` serves single lookups; the method deliberately shares its name with the `VocabEntry` type it returns. No iterator accessor is added.
- **Length-prefixed fields** (`len:value`) for every string in the digest, including ops. `%q` would also work; length prefixes avoid depending on quoting rules.
- **No version salt** in the digest: the contract already says it may change between releases, and the template registry is in-memory.

## Risks / Trade-offs

- `TestCL_VocabMutationDoesNotLeak` builds no engine: before the fix, an engine built while the singleton is mutated would publish a `car → rest` stdlib template under the unchanged memoized fingerprint, and `t.Cleanup` cannot undo that. The engine-level clause of that scenario is covered by the runtime red test on a non-singleton dialect, and by the fact that engines read the vocabulary only through `Vocab()`.
- In that cl test only the `Vocab()["car"]` check discriminates; its fingerprint check passes before and after the fix because `cl.Dialect()` is memoized.
- "Not a persistence format / may change between releases" is documentation only; no test can assert it.
