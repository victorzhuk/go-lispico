## 2. Conversion memo

- [x] 2.1 Declare the memo slot on `largeMap` and factor the two byte-identical conversion arms of `Assoc` (`core/types.go:1118-1123`) and `Dissoc` (`:1155-1160`) into one `(*HashMap).trieRoot()` helper that today does exactly what those arms do; behaviour and charges are unchanged by this task, which exists so the tests of 1.1 can name the field and compile — Go has no signature-only stub for a struct field. Verify the existing `./core` and `./runtime` suites stay green and `go vet` stays clean.
- [x] 2.2 Publish the converted trie into the memo from `trieRoot` with a compare-and-swap, a lost race discarding its own copy, and read it on the update path; verify `large.root` and `large.count` are untouched, that `getByHashKey`, `Len`, iteration order, equality and printing are unchanged for both large forms, and that the tests of 1.1 go green.
  - Measured after the memo landed, by `BenchmarkHashMapFanOutAssoc` at default benchtime. Against a retained `Set`-built receiver the converting first update charges 4400 bytes at n=9, 101328 at n=100 and 1145936 at n=1000 (8464 / 189201 / 1922844 B/op). Each later update against that same receiver charges 632, 548 and 1390 bytes, averaged over the eight updates one benchmark iteration performs — four of them overwriting a key the receiver already holds and four inserting an absent one, so these are mixed-path means rather than per-insert charges; the allocator figures for that same iteration of eight are 9952 / 6120 / 14216 B/op and 41 / 60 / 78 allocations, so the two columns carry different denominators and are not directly comparable. The trie-form arm's steady state is identical at every size — same charge, same bytes, same allocations — which is the memo's contract: once converted, a builder-form receiver costs exactly what a trie-form one costs. The first payment did not move: 1145936 against the 1145784 task 0.1 recorded at this base, 0.013% apart and inside the plan's ten-percent bound.
- [x] 2.3 Clear the memo in `HashMap.Set` so a bulk write after a memoised update cannot leave a stale trie behind; verify a `Set`-then-`Assoc` sequence returns the same map a conversion-free path would.
- [x] 2.4 Charge the conversion once per value rather than once per update; verify the two refusals separately, because they have opposite contracts — a key-domain refusal publishes no memo, since the error precedes the conversion, while an allocation-ceiling refusal is settled outside `Assoc` and so publishes the memo and bills the refusing evaluation, leaving the next update on that value charging only its own path; and verify `-race` is clean over the concurrent-update path.
