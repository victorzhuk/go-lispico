## Context

On a full-base dialect, `applyVocabulary` (`runtime/engine.go:527`) walks the registration's written names and, for each, reads the value and canonical flag from the view, asks `AppendVocabBindings` (`core/dialect.go:399`) for the cells under this Dialect, and then writes back what is not already there. For an identity entry `name → name` whose value is the canonical GoFunc, `AppendVocabBindings` returns a single binding `{(Name: name, Value: v, Canonical: canonical, Func: lisp2)}` — the canonical flag is whatever the registration passed in, not a freshly demoted `false`. `applyVocabulary` then skips `setVocabValue`/`setVocabFunc` because `canon == b.Canonical && v.Equals(b.Value)`, so the cell's flag and value are unchanged. `NewDialect` skips identity entries in its alias loop (`core/dialect.go:304`), so they emit zero aliases, and the lazy template path (`runtime/lazy_template.go:735`) publishes one `stdlibTemplateEntry` per binding — never two. The only observable effect of an identity entry is its presence in `Dialect.Vocab()`/`VocabEntry(name)` and in the fingerprint hash (`core/dialect.go:347`).

## Decisions

### Drop identity entries rather than special-casing them

The entries carry no runtime meaning on a full base: their canonical flag and value are the same cell that already exists, and nothing in `applyVocabulary` or the lazy template path consults the vocab map for an entry whose canonical equals its own name. Skipping them inside `applyVocabulary` would hide the problem instead of removing it, and a future empty-base policy dialect would still need them as allowlist entries, where they are meaningful — there, the entry actually controls whether the stdlib-registered name is reachable through the dialect. On the full base the right answer is to remove them and document that unrenamed builtins stay callable through the stdlib plugin's own registration.

### Single source for the stock definition

Applied after `dialect-declarative-spec`: one unexported `clSpec core.DialectSpec`; `stockDialect` builds it once with `core.NewDialect`. The three duplicated-spec tests — `TestCL_Dialect_StockFingerprint` (`cl/cl_test.go:251`), `TestCL_StockMatchesSpecFingerprint` (`cl/dialect_spec_fingerprint_test.go:22`), and the `vocab` subtest of `TestCL_StockFormTable` (`cl/dialect_parity_test.go:67`) — reach `clSpec` through a new `cl/export_test.go` instead of repeating the spec inline.

## Risks

- A CL program that depends on the cell of `cons`/`list`/`reverse`/`apply`/`type` being non-canonical: the cell's canonical flag is set by the stdlib plugin's own registration (which calls `SetCanonical`) and is not changed by removing the entry, because `applyVocabulary` already short-circuits the identical write. Nothing reads the canonical flag outside VM native ops, which do not include these names. Verify with the CL corpus on both evaluators.
- A reader of `cl.Dialect().Vocab()` or `cl.Dialect().VocabEntry(name)` for one of the dropped names now sees `nil`/`(VocabEntry{}, false)` instead of `{Canonical: name}`. The fingerprint hash changes for the same reason. No disk state holds either.
