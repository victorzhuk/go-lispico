## 2. Conversion memo

- [ ] 2.1 Declare the memo slot on `largeMap` and factor the two byte-identical conversion arms of `Assoc` (`core/types.go:1118-1123`) and `Dissoc` (`:1155-1160`) into one `(*HashMap).trieRoot()` helper that today does exactly what those arms do; behaviour and charges are unchanged by this task, which exists so the tests of 1.1 can name the field and compile — Go has no signature-only stub for a struct field. Verify the existing `./core` and `./runtime` suites stay green and `go vet` stays clean.
- [ ] 2.2 Publish the converted trie into the memo from `trieRoot` with a compare-and-swap, a lost race discarding its own copy, and read it on the update path; verify `large.root` and `large.count` are untouched, that `getByHashKey`, `Len`, iteration order, equality and printing are unchanged for both large forms, and that the tests of 1.1 go green.
- [ ] 2.3 Clear the memo in `HashMap.Set` so a bulk write after a memoised update cannot leave a stale trie behind; verify a `Set`-then-`Assoc` sequence returns the same map a conversion-free path would.
- [ ] 2.4 Charge the conversion once per value rather than once per update; verify the two refusals separately, because they have opposite contracts — a key-domain refusal publishes no memo, since the error precedes the conversion, while an allocation-ceiling refusal is settled outside `Assoc` and so publishes the memo and bills the refusing evaluation, leaving the next update on that value charging only its own path; and verify `-race` is clean over the concurrent-update path.
